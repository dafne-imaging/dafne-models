# dafne-models — writing plugins

This repo generates `.model` plugin files for Dafne (a medical image segmentation
tool). A plugin is a Python object (`dafne_dl` model class) whose functions are
serialized with `dill` and shipped as a single `.model` file, later loaded and run
inside the Dafne app / server.

Reference material lives in sibling repos, checked out next to this one:

- `../dafne/docs/model_plugin_api.md` — the authoritative API reference for model
  plugins (function signatures, `data` dict keys, metadata schema). **Read this
  file in full before writing a new plugin** — it is short and answers most
  questions.
- `../dafne-dl/src/dafne_dl/` — the model classes themselves:
  - `DynamicDLModel.py` — Keras/TF, single model, 2D by default
  - `DynamicTorchModel.py` — PyTorch, single `nn.Module`, 2D by default
  - `DynamicEnsembleModel.py` — PyTorch, list of `nn.Module` (folds), 3D by default
  - `DynamicTorchFLAREModel.py` — PyTorch FLARE-style, extra preprocess/postprocess hooks
  - `DynamicDummyModel.py` — **weightless wrapper for external pipelines that
    manage their own weights** (e.g. TotalSegmentator, nnU-Net-based tools).
    Only `apply_model_function` (and optionally `incremental_learn_function`) is
    serialized; no `init_model_function`, no weights, no federated learning.
- `../dafne-dl/src/dafne_dl/model_loaders.py` — `ensure_dependencies()`, used to
  pip-install a model's declared dependencies at load time via `flexidep`.
- `src/dafne_models/common.py` (this repo) — `generate_convert()`, the helper used
  to package **weight-bearing** models (DynamicDLModel/DynamicTorchModel/
  DynamicEnsembleModel/FLARE). Handles loading default weights, building the model
  object, dumping the `.model` file and a sidecar `.json` metadata file.

## Two very different kinds of plugin in this repo

1. **Trained-weights models** (`kidney2`, `rectal_cancer`, `sheffield_kidney*`,
   `aschoplex`, `think_ms`, ...): a `generate_<name>_model.py` script defines
   `init_model_function`/`model_apply_function`/`model_learn_function` (all with
   local imports) and calls `generate_convert(...)` from
   `dafne_models.common`, passing a `default_weights_path` to load actual trained
   weights (Keras `.h5`, torch `.pt`/`.pth`, or per-fold ensemble weights).
   Many of these `generate_*.py` files are **auto-generated by the model trainer
   GUI** (`create_model_ui.py`) and marked "Do not edit" — treat those as
   generated artifacts, not hand-written plugin code.

2. **External-pipeline wrapper models** (`TotalSegmentator*`, see
   `generate_totalsegmentator_model.py`): use `DynamicDummyModel` directly (not
   `generate_convert`). There are no weights to package — the wrapped tool (e.g.
   TotalSegmentator, a nnU-Net checkpoint downloaded on first run) manages its own
   weights at runtime, typically cached under an `appdirs`-based Dafne data
   directory. **This is the pattern to use when the user asks for a plugin "like
   TotalSegmentator" or wrapping some other existing external segmentation tool.**

## How to write a `DynamicDummyModel`-style plugin (the TotalSegmentator pattern)

Use `generate_totalsegmentator_model.py` as the template. Structure:

```python
from dafne_dl.DynamicDummyModel import DynamicDummyModel

def apply_<name>(modelObj, data):
    # ALL imports local — this function body is serialized as source via dill
    # and re-executed in a fresh process, so nothing from module scope survives.
    import numpy as np
    ...
    # data['image'] : np.ndarray, data['affine'], data['resolution'],
    # data['classification'] (body-region + optional ",<variant>" suffix), etc.
    # See ../dafne/docs/model_plugin_api.md for the full data dict schema
    # (differs between 2D and 3D models).

    # Locate/download weights to a Dafne-owned directory, not the tool's default
    # (~/.cache, ~/.<tool>), so multiple users/installs don't collide:
    from appdirs import AppDirs
    app_dirs = AppDirs('Dafne', 'Dafne-imaging')
    weights_dir = os.path.join(app_dirs.user_data_dir, '<tool>_weights')
    os.makedirs(weights_dir, exist_ok=True)
    os.environ['<TOOL_WEIGHTS_ENV_VAR>'] = weights_dir

    # modelObj.device is a torch.device — respect it for GPU/CPU selection.

    # Run the external pipeline, convert its output segmentation into
    # {label_name: uint8 binary mask} and return it.
    return {label_name: mask, ...}

model = DynamicDummyModel(
    model_id='<generate a UUID with uuid.uuid4()>',
    apply_model_function=apply_<name>,
    timestamp_id=<fixed int>,   # fixed so repeated runs produce a stable filename
    data_dimensionality=3,      # or 2
    metadata={
        'model_name': '<Display Name>',
        'model_type': 'DynamicDummyModel',
        'dimensionality': '3',
        'variants': ['', 'SomeVariant', ...],   # '' = default/full variant
        'categories': [['Modality', 'ToolName']],
        'orientation': '',
        'info': {
            'Description': '...',
            'Author': '...',
            'Modality': 'CT' | 'MRI' | ...,
            'Reference': '<paper citation>',
        },
        'dependencies': {
            'pip-package-name': 'pip install spec, e.g. "package >= 1.2"',
        },
    },
)

# Save: <model_name_prefix>_<timestamp>.model + a sidecar <model_name_prefix>.json
# (see save_model() in generate_totalsegmentator_model.py)
```

Key points specific to this pattern:

- **No `init_model_function`.** `modelObj.model` stays `None`; the wrapped tool
  loads/builds its own network internally.
- **Weights are not bundled.** `get_weights()`/`set_weights()` are no-ops;
  `calc_delta`/`apply_delta`/`factor_multiply` raise `NotImplementedError` —
  these models cannot participate in federated learning or weight arithmetic.
  Don't try to work around this.
- **`data['classification']`** commonly encodes `"<BodyRegion>"` or
  `"<BodyRegion>,<Variant>"` — split on `,` to read the variant when the model
  declares multiple `variants` in metadata (see the `CT_VARIANT_SUBSETS` /
  `MR_VARIANT_SUBSETS` dicts in the TotalSegmentator script for the idiom of
  mapping a variant name to a subset of output labels).
- **`metadata['dependencies']`** is a dict of `{pip_package: pip_install_spec}`.
  These are installed at *model load time* on the end user's machine via
  `ensure_dependencies()` / `flexidep` — not at generation time. Since imports
  are local to the function body, the generator script itself does not need the
  wrapped tool installed to produce the `.model` file, but it's still useful to
  have it installed locally for testing `apply_model_function` manually before
  packaging.
- **Save both a `.model` and a `.json`** (metadata-only, human-readable) sidecar
  file, named `<Prefix>_<timestamp>.model` / `<Prefix>.json`, written to a
  `models/` output directory (first CLI arg, default `'models'`).
- Pick a **fixed `timestamp_id`** (not current time) so re-running the generator
  produces the same filename/version rather than a new one each time.
- Generate the `model_id` UUID once and hard-code it — it's the model's stable
  identity across versions/re-generation.

## General plugin-writing checklist (applies to both patterns)

1. Read `../dafne/docs/model_plugin_api.md` for the exact `data` dict keys for
   the dimensionality (2D vs 3D) you're targeting, and the return shape
   (`{label_name: np.ndarray(uint8)}`).
2. **Every import inside every serialized function must be local** — no
   module-level imports feed into `init_model_function`, `apply_model_function`,
   `incremental_learn_function`, or the FLARE pre/postprocess functions.
3. Decide which pattern applies:
   - Wrapping an external tool/pipeline with its own weight management →
     `DynamicDummyModel` (see above).
   - Packaging a model you trained yourself (Keras/PyTorch/ensemble) whose
     weights ship with the plugin → use `generate_convert()` with the
     appropriate `model_type`.
4. Fill in `metadata` thoroughly: `model_name`, `categories` (hierarchical path
   shown in the Dafne UI), `variants`, `info` (Description/Author/Modality/
   Reference), `dependencies`. `dimensionality`, `type`, and
   `can_incremental_learn` are auto-added by the base class at runtime — don't
   worry about setting them redundantly beyond what `generate_convert`/your
   script already sets.
5. Test `apply_model_function` standalone (call it directly with a hand-built
   `data` dict) before wrapping it in the model object — errors inside a
   `dill`-serialized function are harder to debug after the fact.
6. Output goes to a `models/` directory: `<Prefix>_<timestamp>.model` plus a
   `<Prefix>.json` metadata sidecar.

## MuscleMap (`../MuscleMap`)

`generate_musclemap_wholebody_model.py` reimplements MuscleMap's whole-body
muscle segmentation model as a native `DynamicTorchModel` (bundled weights,
real `incremental_learn`, full federated-learning support) — not a
`DynamicDummyModel` wrapper, unlike the TotalSegmentator plugin above.

- **Whole-body is the only MuscleMap model this repo targets.** MuscleMap also
  publishes region-specific models (abdomen, forearm, leg, pelvis, thigh), but
  those are frozen/unmaintained upstream — do not add plugins for them.
  `generate_musclemap_thigh_model.py`, if still present, is retired; treat
  the whole-body plugin as the only one to extend or fix.
- The whole-body weights on Zenodo are versioned (`../MuscleMap/scripts/mm_util.py`'s
  `ZENODO_MODELS['wholebody']`); resolve the true latest version via
  `https://zenodo.org/api/records/<concept_id>/versions/latest` (follow the
  redirect) rather than trusting a `versions` dict that may be stale in a
  local checkout — it lagged behind by a full version (1.3 vs. actual
  latest 1.4) last time this was done. Architecture params (`out_channels`,
  `num_res_units`, etc.) and the label list are NOT stable across versions —
  re-derive them from that version's `contrast_agnostic_wholebody_model.json`
  every time you bump the bundled weights, and verify the new `.pth`'s state
  dict actually loads into the rebuilt `UNet` before committing to it.
- **Reproduce MuscleMap's pre/postprocessing exactly**, not just approximately
  — read `../MuscleMap/scripts/mm_segment.py`'s `pre_transforms`/
  `post_transforms` and `mm_util.py`'s `run_inference`/`connected_chunks` line
  by line rather than working from memory of a similar model. Specific
  details that are easy to get wrong (and did, the first time this was
  written) and silently degrade output quality without erroring:
  - `SpatialPadd`'s target size is **hardcoded to 256x256**, independent of
    that region's `roi_size` used for the sliding-window ROI.
  - `CropForegroundd`'s default foreground threshold (`value > 0`) runs
    **after** `NormalizeIntensityd`, i.e. on the already-normalized image,
    not on the raw nonzero mask.
  - Most importantly: `Invertd` (which resamples the network's per-class
    output back to native resolution, with **linear** interpolation) runs
    **before** `AsDiscreted(argmax=True)`. Discretize only after resampling
    back to native resolution — do not argmax at model resolution and then
    nearest-neighbor-upsample the label map; that loses boundary precision
    and visibly degrades results.
  - `run_inference` finishes with `connected_chunks()`, which keeps only the
    largest connected component per label. Dafne's 2D per-slice API has no
    equivalent of the full-volume 3D version of this, but applying it per
    label within each 2D slice is a reasonable analog and measurably reduces
    stray specks.
  - The CLI's sliding-window `overlap` defaults to 90% (`--overlap 90`), not
    a lower value chosen for speed.
- **2D models in the live Dafne app receive RAW, un-reoriented slices — no
  canonicalization at all.** This was gotten wrong twice before landing on
  the right fix; both wrong turns are recorded here because the failure mode
  is silent (no error, no shape mismatch, just degraded predictions) and
  easy to reintroduce:
  - Wrong turn #1: assumed the live app matches `run_model.py`'s own
    `ensure_compatible_orientation_inplace(image, metadata)` call (reformats
    to `metadata['orientation']='Axial'` → `('LR','AP','SI')`) and "fixed"
    the plugin to expect that convention. This is wrong: in the live app
    (`../dafne/src/dafne/ui/MuscleSegmentation.py`), **only the 3D path**
    (`getSegmentedMasks_3D`) calls orientation canonicalization before
    inference. The 2D path (`getSegmentedMasks`) feeds `data['image']`
    straight from `self.imList[imIndex]`, which is backed by the volume as
    loaded by `dicomUtils`'s `DicomReader`/`NiftiReader` with **no
    reformatting whatsoever** — `run_model.py`'s original (pre-fix)
    unconditional reformat call made it exercise a code path the real app
    never takes for 2D models. Trusting it as ground truth for "what Dafne
    feeds 2D models" gave a misleadingly good ~0.98 Dice while the actual
    live-app-equivalent path scored ~0.11 with the same model file.
  - Wrong turn #2, inside that first (wrong) fix: even granting the
    (incorrect) `('LR','AP','SI')` assumption, a single axis-1 flip was
    applied, based on comparing a `dicomUtils`-reformatted-to-Axial volume
    against `nibabel.as_closest_canonical()` RAS data. That comparison was
    real but answered the wrong question, since the live app never performs
    that reformat step in the first place.
  - **The actual fix**: `run_model.py` now only calls
    `ensure_compatible_orientation_inplace` for 3D models (`if dimensionality
    != 2:`), matching the live app exactly — this makes it a faithful test
    harness instead of a source of false confidence. The plugin's
    `apply`/`incremental_learn` correct Dafne's raw per-slice layout to the
    RAS-like orientation MuscleMap trains against with a **transpose followed
    by flipping both axes** (`image.T[::-1, ::-1]`), not a single-axis flip —
    found by brute-forcing all 8 transpose×flip×flip combinations against
    real ground truth (see below) rather than reasoning about axis codes by
    hand, which is exactly what produced wrong turns #1 and #2. `resolution`
    must be reversed (`resolution[::-1]`) to match the transpose. The inverse
    (`label_map[::-1, ::-1].T`) is applied to the output label map before
    building masks, so masks come back in the same array layout Dafne gave
    the image in. This is tied to Dafne's raw DICOM-loading convention for
    axial acquisitions specifically — if this is ever revisited, re-derive it
    empirically rather than assuming it still holds.
- **To validate a rewrite of the orientation/pre/postprocessing pipeline,
  don't trust your own reimplementation of how Dafne loads/feeds data** —
  reproduce the exact call site instead. For 2D models that means simulating
  `MuscleSegmentation.getSegmentedMasks`: load via `dicomUtils.medical_volume_from_path(path,
  reorient_data=False)`, take `image.volume[:, :, i]` and
  `image.pixel_spacing[:2]` directly, and do **not** call any orientation
  reformatting before `model.apply()` — or equivalently, use
  `dafne-models/src/dafne_models/bin/run_model.py` (now fixed to only
  reformat for 3D models) run with the venv in `../dafne`
  (`../dafne/venv3.12/bin/python3`, which has `voxel`/`dicomUtils`/torch/monai)
  and `PYTHONPATH=src:../dafne-dl/src`. It takes an image/DICOM-directory
  path, `--model <.model file>`, `--classification`, and `--output <dir>`,
  and writes one `<Label Name>.nii.gz` per predicted label. When the correct
  orientation transform for a 2D model isn't obvious from reasoning about
  axis codes, brute-force it: generate a variant of the plugin with no
  orientation correction, try all transpose/flip combinations against real
  ground truth, and pick whichever maximizes Dice — this is what actually
  found the transpose+double-flip fix above, after two rounds of
  axis-code reasoning got it wrong.
- For the ground-truth side, `/media/bigboy2/dicom/dafne_data/Thigh/` (a real
  DICOM series, as the live app would actually load — note it also contains
  Dafne's own leftover `rois*.p`/`transforms.p` pickle files from prior
  sessions in the same directory; `dicomUtils` fails loudly but harmlessly
  trying to read those as DICOM, ignore those errors) and, equivalently,
  `../MuscleMap/thigh.nii.gz`/`../MuscleMap/thigh_dseg.nii.gz` (same
  underlying scan as a NIfTI pair; the latter has no label names, only
  MuscleMap's raw sparse label codes, e.g. `7101`) are a real already-segmented
  example **produced by the wholebody model** (its labels use wholebody's
  sparse coding scheme, not the thigh region model's 1..28 scheme) despite
  the filename/directory being named "Thigh" — always run this through the
  wholebody plugin, never the (retired) thigh one. Per-label Dice, computed
  directly between `run_model.py`'s output NIfTIs and `thigh_dseg.nii.gz`
  (both land on the same physical grid/affine already — no reorientation
  needed for the comparison itself), is a good summary metric. The
  fully-corrected pipeline scores ~0.98 mean Dice on this ground truth,
  confirmed identically via both `run_model.py` and a direct simulation of
  the live app's own calling convention.
